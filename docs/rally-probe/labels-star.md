## 判定

**検出可能だが要工夫**（系統ごとに難易度が大きく違う）

| 系統 | 中身 | 判定 | 根拠 |
|---|---|---|---|
| **B系統 コールアウト** | Out / Net / Body Shot / Change Court | **検出容易** | 12本 2時間35分の全走査で **FP 0 / FN 0**。バンド内の絶対輝度 1条件で決まる |
| **C系統 MATCH POINT** | 画面中央の大型テキスト＋コーナーバッジ | **検出容易** | 固定位置・大サイズ。ただし色はアニメで変わる |

| **A系統 コート上ラベル** | SMASH / GOOD / NICE | **検出可能だが要工夫** | ROI をコート内側に切れば分離できる（e=0.25〜0.34 対 背景 ≤0.21）が、マージンは狭い |

**ラリー解析にとっての価値の順**:
1. **Out / Net** = ポイントの決着理由がそのまま文字で出る（ただし 2時間35分で各3回と稀）
2. **星マーカー** = 「高い球（ロブ）が上がった」の確実なマーカー。**ラリーの42%に出る**
3. **Change Court** = ゲームの切れ目（ラリー長の集計から除外すべき区間の目印）
4. **SMASH / GOOD / NICE** = ショット品質の評価。頻度は高いが意味の解釈が要る

### ラベルは「2系統」ある

**(A) コート上ラベル（ラリー中・ワールド座標に貼り付く）**

  テキスト「SMASH」**虹グラデ（左=緑→黄→橙→右=赤）**＋**太い黒アウトライン**
- **位置は固定でない**。ボールの着弾マーカー（星）のすぐ上に出て、カメラのパンと一緒に動く
  - 10-44-35 t=388.5 → FHD (545..755, 733..790)
  - 01-08-30 t=119.0 → FHD (981..1191, 843..902)
- 文字高さ（黒縁込み）FHD ≈ 55〜60px。アイコン込み全幅 FHD ≈ 210px

**(B) 画面中央の暗バンド上のコールアウト（ポイント/ゲームの節目）**
- 実例「Body Shot」（黄・太字イタリック）: 00-39-45 t=119.8〜121.25（1.45秒）, t=104.5〜105.9

- コールアウト文字: 黄 = r>200 && g>170 && b<115 / 白 = lum>215 && max-min<40。バンド内 x 160..1760
- SMASH ラベル: 虹グラデ＋黒縁。緑画素 = g>150 && g>r+45 && g>b+55 / 赤画素 = r>185 && g<105 && b<105
  / 黒縁 = lum<45。FHD 128x64 のブロックに緑・赤・黒が同居する条件で拾える（緑の壁・赤土コートで
  誤検出するので要ガード）

## 推奨アルゴリズム

前提: 全部 **1920x1080 換算の比率**で持つ。実装は `cropRegion`（実解像度へ自動スケール）と同じ流儀。
検出は**縮小フレームで十分**（下記の解像度で全部実測済み）。1本12〜17分の動画を全走査して
ffmpeg デコード込みで **40秒前後**（Node・1スレッド）だった。本番は WebCodecs で同等以上。

### B系統: 暗バンド＋コールアウト（Out / Net / Body Shot / Change Court）— **最優先で実装すべき**

**入力**: 画面の y = 0.315〜0.704 の帯だけを **64x42** に縮小（1行 ≒ FHD 10px）。5fps で足りる。

```js
// 縮小フレーム(64x42)。中央のテキスト列を避けて左右の帯だけで背景輝度を測る
const XS = [[2,20],[44,62]];
const inner = meanL(rows 13..27, XS);   // FHD y 470..610 ＝ バンド内側
const above = meanL(rows  4..11, XS);   // FHD y 380..450
const below = meanL(rows 30..38, XS);   // FHD y 640..720
const isBand = inner < 55 && Math.min(above, below) - inner > 45;
```
- **12本 2時間35分の全走査で FP 0 / FN 0**（43件すべて真、既知の4件も全部再現）。
- `inner<55` の絶対条件が効く理由: バンドは**強い暗幕**で、どのコートでも内側が L=14〜44 に落ちる。
  ネットのメッシュは L=76〜130 までしか落ちない。夜森コート（最暗）でも inner=22 / above=112 で余裕。
- **連続 0.6秒以上**（5fpsで3フレーム以上）を1イベントにまとめる。実測は 0.8〜1.6秒。

**語の判定**（バンド内 x=1..63 / y=13..27 のテキスト画素の外接幅・FHD換算）:
```js
isYel = r>170 && g>140 && b<120 && (r-b)>90;    // Out / Net / Body Shot
isWht = L>190 && (max-min)<50;                   // Change Court
// 幅で3群に分ける（実測）
//   90〜120px  かつ 黄 →「Out」または「Net」  ← 字形照合が必要（下記）
//  330〜360px  かつ 黄 →「Body Shot」
//  420〜480px  かつ 白 →「Change Court」
```
- **Out と Net の区別だけ字形照合が要る**。バンド内は背景が一様に暗いので、
  `mask(img,'lightink')` 相当（適応閾値の明色インク）＋ `segment()` で 3グリフに割れる。
  3文字なので `readGlyphs` に O/U/T/N/E の5テンプレを持たせれば十分。
  **フォントは Change Court と同じ**（太字イタリック）なので、Change Court の C/h/a/n/g/e/o/u/r/t を
  収穫すれば O・N・E・T は流用できる。
- 意味づけ: **Out = ラリー終端の理由「アウト」**、**Net = ラリー終端の理由「ネット」**、
  **Body Shot = 相手に球が当たった**、**Change Court = ゲーム間のコートチェンジ**（ラリーではない）。
- **ただし Out / Net は 2時間35分で各3回しか出ない**。全ポイントの決着理由が取れるわけではない。
  「出たら確実」の高精度・低頻度シグナルとして扱うこと。

**誤検出ガード（夜/暗コート）**: `inner<55` だけだと**画面全体が暗転する演出**（フィーバー発動カットイン・
リプレイ導入・試合間の暗転）も通る。必ず `min(above,below) - inner > 45` を併用すること。
実測で `01-08-30 @69.6-72.0 / @368.2-370.8`（inner=20 の 2.6〜2.8秒）はこの条件で正しく落ちた。

### A系統: コート上のカラーラベル（SMASH / GOOD / NICE）

**入力**: フレーム全体を **480x270** に縮小。5fps。

```js
// 1) 2つのマスク
D = L < 55;                                        // 太い黒縁
V = max(r,g,b) >= 170 && (max-min)/max >= 0.50;    // 高彩度・明るい塗り
// 2) D を 2px 膨張し、V との積 E を作る（＝「黒縁に接した色つき画素」）
E = V & dilate(D, 2);
// 3) ROI（コート内側）に限って 56x16 窓（FHD 224x64）を step4 で走査し E 率を取る
ROI: x = 0.16W .. 0.86W, y = 0.17H .. 0.90H
hit if eFrac >= 0.245
```
- 実測: ラベルの窓は **e = 0.25〜0.34**、コート面/影/白線は **e ≤ 0.21**。
  クレイ赤・ウッド・芝の3コートで同じ閾値が通った（芝は S が高いコートだが、
  「黒縁に隣接」の条件が効いて誤発火しない）。
- **ROI を切らないと使い物にならない**（実測）。画面左右端の観客席・審判台・レンガ縁石が
  e=0.20〜0.35 を出して常時勝ってしまう。court-robustness.md の
  「FPの主犯はコート外」がここでもそのまま当てはまる。
- 16分の動画で 103セグメント／9.5分で 61／12.8分で 72。うち真ラベルは半分弱。
  残りは MATCH POINT・レートパネル・試合間バナー・ネットに当たったボールなど。
  **HUD点灯中（ラリー中）に絞ればさらに減る**。

**語の判定**（候補窓を FHD に戻して切り出し、以下の3特徴で分類）:
```js
darkFrac = frac(L < 50);                       // 黒縁の量
hueBins  = 30°刻みヒストグラム（S>0.5 かつ V>0.6 の画素のみ）
nHues    = hueBins のうち 1.5% 以上の本数
// SMASH : nHues >= 4（虹）                       実測 6本 / darkFrac 0.23
// GOOD  : nHues == 1 かつ 主色相 60°帯（黄緑）   実測 1本 / darkFrac 0.32
// NICE  : nHues 1〜2 かつ 主色相 0〜30°帯（橙赤） 実測 darkFrac 0.3 前後
```
- 確実にしたければ、この3語は語彙が固定なので **`textVec` + `profileXcorr` の辞書照合**に落とす。
  インクマスクは白ではなく `E`（黒縁隣接の色つき画素）を使う。**平行移動に強い profileXcorr が
  そのまま使える**（ラベルはワールド追従で毎回位置が違うため、位置不変の照合が必須）。
- **SMASH は出現直後を採る**。退色すると darkFrac が 0.23→0.03 に落ちて検出も分類も崩れる（実測）。
- SMASH には左に **4つ丸のボタンアイコン**（大白丸1＋白リング黒芯3、FHD 約 60x55）が付く。
  これは**白と黒だけ**なので、既存 `findBanner` の `pureWhite` インクでそのまま拾える。
  SMASH の確証を取りたいときの副シグナルに使える。

### C系統: MATCH POINT
- 画面中央上寄り（窓左上 FHD ≈ (816,560)）に 0.8〜1.2秒。A系統と同じ検出器に **e ≥ 0.35 かつ

### 星マーカー

**入力**: フレーム全体を **320x180** に縮小。5fps。

```js
// 1) 金色画素
const isStarGold = (r,g,b) => {
  const [h,s,v] = hsv(r,g,b);
  const gold = (r+g)/2 - b;                  // goldness
  return h >= 38 && h <= 63 && v >= 0.70 &&
         (s >= 0.66 || gold >= courtGold + 22);   // ← 砂対策の第2枝
};
// courtGold = そのフレームのコート面の goldness 中央値（COURT_FAR ∪ COURT_NEAR）
// 実測: 星 = 141〜146（クレイ・砂で同値）／クレイ面 53／砂面 117

// 2) 連結成分 → 遠近スケール込みの形状フィルタ（cx,cy,bw,bh は FHD 換算）
const expW = 145 + 0.175 * (cy - 300);           // 実測にフィットした線形モデル
const ok = cy >= 250 && cy <= 1010 &&
           bw >= expW * 0.60 && bw <= expW * 1.55 &&
           bh >= 30 && bh <= 130 &&
           (bw / bh) >= 1.5 && (bw / bh) <= 3.8 &&
           area320 >= 40;                        // 320x180 での連結成分面積
// 3) 除外: 下隅HUD（y>0.90H かつ x<0.15W|x>0.85W）・左上吹き出し（y<0.26H かつ x<0.24W）・
//          上端の球速板/FVゲージ（y<0.10H）
// 4) 連続 0.2秒以上を1イベントに統合（サンプルは 10fps 推奨。5fps だと 1コマだけの星がある）
```
- クレイ赤・芝・ウッドでは `s>=0.66` の第1枝だけで足りる（クレイで目視 34コマ中 30コマ真＝**精度88%**）。
- **砂だけは第1枝が破綻する**（砂面の S90 が 0.66〜0.72 で星と重なる）。
  goldness の相対枝を必ず併用すること。それでも砂は誤検出が多いので、
  砂では**「垂直な光の柱」の併用**を推奨（星の中心から真上に伸びる淡黄色の細い柱。
  幅 FHD 10〜20px・高さ 200〜500px。星より背景と分離しやすい）。
- **奥コートの誤検出源**: 芝・ウッドでは奥コート候補の多くが誤検出だった
  （`11-33-43 @119.6 / @326.6 / @668.0 / @680.6 / @698.8 / @704.4`、`00-39-45 @165.4 / @436.2` は全部空振り）。
  クレイでは逆に奥コート候補 9件中 7件が本物。**奥コートの精度はコート依存**。
  奥だけで検出したラリーは「星あり」と断定せず、SMASH ラベルや「垂直な光の柱」との共起で裏を取ること。
- **SMASH ラベル自身が金色フィルタに引っかかる**（`22-02-04 @233.4` 実測: 面積87・箱32x13）。
  A系統の検出結果とバウンディングボックスが重なる候補は星から除外すること。

**ラリー単位への集約**（deuce-pips.md の HUD 消灯法と組み合わせる。今回この組み合わせで実測した）:
```
1) 左右コーナーのピル占有率 fillL/fillR を 5fps で計算（deuce-pips.md の座標）
2) hudOn = fillL>0.25 && fillR>0.25
3) hudOn=false が 1.2〜4.5秒 → ポイント境界 / 4.5秒超 → ゲーム間・試合間（別扱い）
4) ラリー = 前の境界の終わり+0.2秒 〜 次の境界の始まり
5) そのラリー窓に入る星イベントを数える
```
- この手順で `10-44-35` は 26ポイント、`22-02-04` は 38ポイント、`11-33-43` は 25、`00-39-45` は 20 が取れた。
  **境界の見落としは目視した範囲では無し**。

## findBanner の改修案（色つき文字への拡張・そのまま貼れる形）

現状 `tools/vision.js:521` の `isTextPx` が `lum>225 && (max-min)<45` にハードコードされている。
**インク述語を差し替え可能にするだけで A系統・B系統の両方に流用できる。**

```js
// vision.js に追加
const INK = {
  // 既存: フィーバー発動バナー（巨大白文字＋斜めリボン）。挙動を変えないこと
  pureWhite:     (r,g,b) => lum(r,g,b) > 225 && Math.max(r,g,b)-Math.min(r,g,b) < 45,
  // B系統・白: 「Change Court」。背景が暗幕なので 225 は厳しすぎる（実測ピークで 190〜230）
  calloutWhite:  (r,g,b) => lum(r,g,b) > 190 && Math.max(r,g,b)-Math.min(r,g,b) < 50,
  // B系統・黄: 「Out」「Net」「Body Shot」（と勝者画面の「Winner」）
  calloutYellow: (r,g,b) => r>170 && g>140 && b<120 && (r-b) > 90,
  // A系統: 「SMASH」「GOOD」「NICE」。色相を問わず「明るい高彩度」だけを見る
  vividInk:      (r,g,b) => { const mx=Math.max(r,g,b), mn=Math.min(r,g,b);
                              return mx >= 170 && (mx-mn)/mx >= 0.50; },
};

function findBanner(video, region, opts = {}) {
  const isTextPxFn = opts.ink ?? INK.pureWhite;          // ← 追加
  const needRibbon = opts.needRibbon ?? true;            // ← 追加
  const darkMin    = opts.darkMin ?? 0.10;               // ← 追加
  ...
  const isTextPx = i => isTextPxFn(data[i*4], data[i*4+1], data[i*4+2]);
  ...
  if (needRibbon) { /* 既存の ribbon < 0.15 で return null */ }
  if (darkIn < darkMin) return null;
  ...
}
```

呼び分け（すべて今回の実測値に合わせた）:

| 用途 | region | opts |
|---|---|---|
| フィーバー発動バナー（既存） | `bannerBand` | 変更なし |
| **Change Court** | `{x:0,y:455,w:1920,h:165}` | `{ink:INK.calloutWhite, needRibbon:false, minTotal:600, minW:380, minH:28, maxH:70}` |
| **Out / Net / Body Shot** | 同上 | `{ink:INK.calloutYellow, needRibbon:false, minTotal:150, minW:70, minH:24, maxH:70}` |
| **SMASH / GOOD / NICE** | A系統の候補窓（±40px 余白） | `{ink:INK.vividInk, needRibbon:false, darkMin:0.15, minTotal:400, minW:100, minH:24, maxH:80}` |

- **`needRibbon:false` は必須**。ribbon 判定（箱の下 26px に高彩度帯があるか）はフィーバーバナー専用で、
  暗バンドにもコート上ラベルにも斜めリボンは無い。
- **`minTotal` は解像度依存**。現状 2500 は FHD 前提の絶対値なので、
  720p では 1/2.25 に減る。`minTotal * (videoWidth/1920)**2` にすること
  （これは既存のフィーバーバナー検出にも効いている潜在バグ。サンプル12本中7本が720p）。
- `darkIn`（黒縁率）はそのまま使える: SMASH=0.23 / GOOD=0.32 / 暗バンド上の文字は背景が真っ暗なので当然通る。
- 返り値の `profile`（列プロファイル）と `profileXcorr` は**そのまま流用できる**。
  A系統ラベルは毎回位置が違うので、平行移動に強いこの照合が最適。

## 落とし穴
- **findBanner（純白 lum>225・max-min<45）では「SMASH」「Body Shot」は絶対に拾えない**。
  SMASH は虹グラデ（彩度が高い）、Body Shot は黄。純白条件を外す改修が必要（上記）。
- 「ドロドロショット」はラケットバナーそのもの。ラベル検出の新規対象にしなくてよい。
- ~~暗バンド検出は夜/森コートで誤検出しやすい~~ → **実際の誤検出源は「夜コート」ではなく
  「明るいコートのネットのメッシュ」だった**（砂 10-44-35 で実在1件に対し FP 11件）。
  夜森コート 11-02-43 は暗いのに FP ゼロ。**「上下との差」ではなく「バンド内の絶対輝度 < 55」で判定すること**。
- **A系統ラベルの検出は ROI をコート内側に切らないと成立しない**。画面端の観客席・審判台・
  レンガ縁石が常に最高スコアを取る（実測 e=0.20〜0.35 でラベルと同レンジ）。
- **SMASH は退色する**。黒縁率が 0.23 → 0.03 に落ちるので、遅いフレームで採ると検出も分類も落ちる。
- **星マーカーにルールK（S > S90+0.08）は使えない**。砂コートで星の S=0.66〜0.73 に対し
  砂の S90=0.66〜0.72 で完全に重なる。goldness=(r+g)/2−b の相対差（+25〜29）だけが頼り。
- **ショットのオレンジ／黄トレイルが星の形状フィルタを通る**（芝・ウッドの奥コートで実測8件）。
  奥コート候補は精度が落ちるので単独では信用しないこと。
- **星の面積しきい値を1本値で持つと奥コートの星を全部落とす**（実測: 手前 260x110 に対し奥は 110x40）。
  最初この誤りで「星は自分側にしか出ない」と誤結論しかけた。**必ず y 依存のサイズモデルにすること。**
- **ダブルスでは星の出現率が明確に低い**（25% 対 シングルス 44〜50%）。ダブルス動画で閾値を検証すると
  「出ない」と誤結論しかねない。
- **5fps サンプリングでは星を取りこぼす**。持続 0.2秒（1コマ）の例が実在する。
  実際、2fps のタイル目視で「星なし」と判定したラリー（`22-02-04` 580〜595秒）に、
  5fps 検出では星が2つあった（@585.0 / @591.2・いずれも実フレームで確認）。**目視のFN確認は 5fps 以上で行うこと。**
- 得点ピップのHUD消灯でラリーを切ると、**Change Court やリプレイを含む「長いラリー」ができる**
  （実測で 30〜44秒のものが数本）。ラリー長を使う分析では B系統の Change Court を引き算すること。

  1440p は 6Mbps で色ノイズが最大なので、彩度ベースの判定が最も苦しい条件になる。

- **MATCH POINT が「どちら側の」マッチポイントかを画面から読む方法**。色はアニメーションで変わるので使えない。
  実測した3例はすべて相手側のマッチポイントで、大型テキストの見た目に差は無かった。
  結局**得点ピップから判断するしかない**可能性が高い（deuce-pips.md の方式）。
- **MATCH POINT のコーナーバッジの正確な座標**（左下/右下のどこに、どのサイズで出るか）を実測していない。
- **「Winner」（勝者画面の黄文字）の正確な座標**。00-39-45 @205.0 でキャラアップ画面の左下にあることは
  目視したが、座標も色も数値化していない。
- **A系統ラベルが「どちらのプレイヤーに対する評価か」**。ワールド追従で打った側の近くに出るはずだが、
  打者との対応を検証していない（GOOD が自分の good なのか相手の good なのか）。
- **リプレイ/スロー演出中にラベルが再表示されるか**。二重カウントの危険があるが未確認。
