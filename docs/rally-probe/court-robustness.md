# コート別背景色と誤検出リスク

調査日 2026-08-24 / 担当 court-robustness / 全数値は **1920x1080 に正規化した座標・画素値**（実解像度は F0 参照）
色空間は HSV（H=0-360, S=0-1, V=max(R,G,B)/255）、L = 0.299R+0.587G+0.114B。

## 判定

**検出可能だが要工夫。**

- 「トップスピン=赤 / スライス=青 / フラット=紫 / ロブ=黄 / ドロップ=白」を**固定RGB閾値のマスクで拾う設計はコート横断で完全に破綻する**。
  クレイ赤では**コート面の86%が赤判定**、青ハードでは**コート面の88%が青判定**になる（実測、後述F3）。
- 一方、**「そのフレーム自身のコート面の彩度・明度分布を基準にした相対判定」なら全9コートで成立する**。
  実測した推奨式（ルールK）で、ショットのビーム/尾は 57〜82% の画素が拾え、コート面の誤検出は最悪 2.5%。**20〜40倍の分離**が取れる。
- コートのラインは**全9コートで白く（低彩度・高輝度）取れる**。石畳・ウッド・船も問題なし。単一マスクでライン骨格が抽出できた（F5）。
- 得点ピップは**全コートで完全不透明**。背景は一切透けない。コート非依存に読める（F6）。
- ただし **カメラはラリー中に固定ではない**（水平に数百px動く）。背景時間中央値との差分は**そのままでは使えない**（F4）。

**日向/日陰で発火が反転する（重要）**
マスク像を目視して分かった、閾値表を作るうえで致命的な性質:
- **砂**: オレンジが発火するのは **NEAR（やや影）だけ**。日向の FAR は明るすぎて B>100 になり発火しない。
- **ウッド／船**: 逆に **FAR（日向の甲板）だけ**が発火し、影の NEAR は暗すぎて発火しない。

→ 発火するかどうかは「コート」ではなく「そのピクセルの明るさ」で決まる。
**コート別に1組の固定閾値を持っても解決しない。**

### F4. カメラはラリー中に固定ではない（背景差分の前提が崩れる）

`22-18-37 @297-302s`（5秒間 / 5fps）でコートラインを追跡:

| 指標 | 動き |
|---|---|
| 手前左サイドラインの x 座標 | **226 → 428 px（振幅 200px）** |
| 奥ベースラインの y 座標 | 244 → 292 → 261 px（振幅 ≈50px） |

`10-44-35 @305-310s`（砂）でも同様: 手前左サイドライン x = **298 → 560 px**。

60fps で細かく測った並進量（SAD最小化、砂 306.0秒起点）:

| 時間差 | 最良 (dx,dy) |
|---|---|
| 0.1秒 | (-1, -1) |
| 0.2秒 | (-2, -2) |
| 0.5秒 | (+5, -5) |
| 1.0秒 | (+30, -2) |

- **0.2秒以内なら 3px 以下**でほぼ静止。
- **1秒で 30px、5秒で 200px 以上**動く。
- 実測: 5秒窓の時間中央値を取ると**コートが完全に滲んでラインが消える**。差分画像では**ライン全部が前景として点灯**した。
- 0.6秒窓（60fps・36枚）に縮めても、**中央値にコートラインの二重像が残る**うえ、
  **ビームが 0.3秒以上持続するため中央値にビーム自体が混入**した。

→ **単純な時間中央値背景差分は不可**。使うなら (a) フレーム間の並進を推定して整合させてから差分、または (b) 0.2秒以下の極短窓＋動きの遅いフレームのみ、に限る。

## 座標・閾値（1920x1080基準・そのまま実装可）

```js
// --- コート面サンプル帯（プレイヤーやラインを含むが中央値で吸収される） ---
const COURT_FAR  = { x:560, y:120, w:800, h:210 };   // (560,120)-(1360,330)
const COURT_NEAR = { x:300, y:700, w:1320, h:200 };  // (300,700)-(1620,900)

// --- コートライン（全9コート共通・実測で検証済み） ---
const isCourtLine = (r,g,b) => lum(r,g,b) > 175 && sat(r,g,b) < 0.20;
//   期待該当率 2〜7%（コート帯内）。石畳は S 条件が効かないが L 条件だけで通る。
```

## 推奨アルゴリズム

### 1. コート基準をフレームごとに測る（コート識別テーブルより優先）

既存アプリはコート識別を実装済みなので「コート別に定数表を持つ」設計は取れるが、
**F3 の日向/日陰反転により、コート単位の固定閾値では足りない**（同じ砂コートでも FAR は発火せず NEAR は 39% 発火）。

代わりに **毎フレーム（またはラリー開始時の数フレーム）でコート基準を測り直す**:

```
1. COURT_FAR ∪ COURT_NEAR を 2px 間引きでサンプル
2. isCourtLine(L>175 && S<0.20) の画素を捨てる
3. 残りの S, V の 90%tile を S90, V90 とする
4. しきい値 = (S90+0.08, V90-0.05)
```

コスト: 約 (800*210 + 1320*200)/4 ≈ 108k サンプル → 60fps でも 1フレーム数ms。
`vision.js` の `frac()` と同じ走査パターンで書ける。

**コート識別の使いどころ**は「閾値そのもの」ではなく **サニティチェック**にする:
測った S90/V90 が上の表と大きくズレたら、演出オーバーレイ中（バナー/MATCH POINT/リプレイ）と判断してそのフレームを捨てる。

### 2. コート多角形の内側だけを見る（FP の主犯はコート外）

マスク像を見た限り、**誤検出の大半はコート外**（レンガ縁石・観客席・船の金装飾・パラソル）。

```
1. isCourtLine マスクを作る
2. 奥ベースライン・両サイドライン・両サービスラインを直線当てはめ（Hough or RANSAC）
3. 交点から台形（またはホモグラフィ）を得る
4. その内側 + 上方向に数百px（打球の弧は空中を通る）だけを解析 ROI とする
```

**手前ベースラインには依存しないこと**（F5 の通り 9コート中5つで画面外/HUD裏）。
カメラが動くので**ラリーごとに1回でなく、数フレームおきに引き直す**。

### 3. ショット色は「絶対色」でなく「コートからの色差ベクトル」で分類する

赤/青/紫/黄/白の分類は、`isRed` のような絶対述語をやめて、
ルールK で抽出した画素群の**代表色相**をコート色相と比較して決める:

```
effectPixels = ルールK に該当し、かつコート多角形内、かつプレイヤー矩形外
blob = effectPixels の連結成分（面積・細長さでフィルタ）
hue  = blob 画素の色相の円環中央値
```

そのうえで色相を 5クラスに割り当てる。実測した色相の目安:
- 赤（トップスピン）系ビーム: H ≈ 0〜20
- オレンジ（尾）: H ≈ 20〜45
- 黄（ロブ）: H ≈ 45〜70
- 紫（フラット）: H ≈ 260〜300
- 青（スライス）: H ≈ 200〜240
- 白（ドロップ）: S が低い → 別枝（後述）

**コート色相と 25°以内に入る組み合わせ**（クレイ赤×赤、砂×黄/橙、ウッド/船×赤/橙、青ハード×青）では、
色相だけで確定させず、**輝度・彩度の差の大きさと、blob が細長い直線状か**を併用する。

### 4. 白系（ドロップ）は別枝で扱う

白いエフェクトは彩度が低いので**ルールK では拾えない**。
一方 F3 の通り `pureWhite`（L>225, max-min<45）は**どのコート面でも 4.6% 以下**なので、
白は絶対閾値のままでよい。ただし**コートラインが同じ条件に入る**ので、
「isCourtLine マスクを膨張させた領域を引き算する」か「静的な直線でない blob だけ採る」処理を足す。

### 5. 背景差分を使うなら動き補償が必須

F4 の通りカメラは 1秒で 30px、5秒で 200px 動く。使うなら:
- 各フレームで直前フレームとの並進 (dx,dy) を推定（`isCourtLine` マスク同士の相互相関か、位相相関）
- 累積して基準フレームへワープしてから中央値を更新
- あるいは **0.2秒（±6フレーム @60fps）以内の極短窓**に限定（実測で 3px 以内）

ただし短窓ではエフェクト自身が中央値に混入する（0.6秒窓で実測）ので、
**背景差分は「補助」に留め、主判定は 1〜3 のフレーム内相対判定にすることを推奨。**

## 落とし穴

1. **面積しきい値を px 絶対値で持つと解像度で 4倍ずれる**。サンプルは 720p / 1080p / 1440p が混在（F0）。必ず 1920x1080 換算か画面比率で。
2. **1440p は 6Mbps しかなく色ノイズが最大**。細い光の柱・小さい星マーカーの検出は 1440p が最悪条件。閾値検証は必ず 1440p 素材（`22-18-37`, `23-19-09`）でも行うこと。
3. **1本の動画に複数コートが入る**。プロファイルは試合単位で切り替える（F1）。
4. **「コート別に固定閾値」だけでは足りない**。同じコートでも日向の FAR と日陰の NEAR で発火が反転する（砂は NEAR だけ橙発火、ウッド/船は FAR だけ橙発火）。
5. **色相での分離を期待しないこと**。実測でエフェクトとコートの色相差は 14〜17° しかなかった（クレイ赤×橙ビーム、砂×橙の尾）。
6. **輝度差の符号が一定でない**。クレイではエフェクトが明るく（+30）、砂では暗い（−34）。「コートより明るいもの」という片側条件で組むと**砂で完全に取りこぼす**（実測: ルールE は砂の尾を 0% しか拾えなかった）。
7. **時間中央値の背景差分はそのままでは使えない**。カメラが動く（5秒で 200px）＋エフェクトが 0.3秒以上持続して中央値に混入する。
8. **誤検出の主犯はコート外**（オレンジのレンガ縁石・金色の船装飾・パラソル・観客席）。ROI をコート多角形に絞れば大半が消える。
9. **キャラクターは必ず全マスクに引っかかる**（明るい高彩度の衣装）。プレイヤー矩形を除外するか、blob の細長さで弾く。
10. **手前ベースラインは 9コート中5つで画面外/HUD裏**。ホモグラフィを手前2隅に依存させない。
11. **石畳では彩度によるライン判別が効かない**（地 S=0.10 vs ライン S=0.04）。輝度差（+125）だけが頼り。逆に石畳の**目地は L=98〜126** で、L>175 なら混入しない。
12. **デュースになるとピップが7個から中央寄せ2個に変わる**（`22-18-37 @310s` で実測）。7個固定のパーサは壊れる。
13. **砂の波紋模様が黄/橙マスクを縞状に誤発火させる**（砂 NEAR で黄 21% / 橙 39%）。ノイズではなく構造的な模様なので、ノイズ除去フィルタでは消えない。
