# カメラ安定性とコート座標変換（ホモグラフィ）調査

座標はすべて 1920x1080 基準。2026-08-24 第2回調査で**完了**（推奨アルゴリズムは 960x540 で通し検証済み）。

## 判定

**検出可能だが要工夫。**（ただし第2回調査で難所はすべて潰れ、実装リスクは低い）

- 「1コート1回の校正」は**不可**。ラリー中もカメラは常時動く
  （実測: 2.3秒でファーベースラインの y が 118→181px、コート横方向は最大245px移動。
   カメラ高さ相当パラメータ `Yc_report` は動画をまたぐと 8.3〜16.1 m と2倍近く振れる）。
- ただしカメラは**回転しない（ヨー・ロール = 0、ピッチ・画角も固定）で平行移動のみ**。
  そのため**消失点が画面上で固定**になり、ホモグラフィは**3自由度**に縮退する。
  → フレーム毎推定が必要だが、**横線2本＋縦線1本を検出するだけ**で厳密に解ける。

**第2回で確定したこと**
- **`xVP = 960`（＝画面中央・厳密）／`yVP = −651`／`K = 2.796e-4` は全コート・全解像度・
  シングルス/ダブルス共通の定数**。7動画・3解像度・10コートで実測（F5・F6）。
  ※前回の 957 は1動画からの推定。**960 に読み替えること。**
- **視点は反転しない。ローカルプレイヤーは常に画面手前**。Change Court 演出があっても不変（F9）。
- **サーブ画は別カメラ**（ロール ±3.3°・消失点が画面内）。標準モデルの適用外（F10）。
- 縦ライン検出は **Hough ではなく `s=(x−960)/(y+651)` の1次元投票**にすると、
  夜の森・石畳を含む**全10コートで5本すべて取れた**（F11・F13・F14）。
- 白線マスクは **`L > max(CL*1.06, 170)`**。下限170が無いと石畳の目地で破綻する（F13）。

## 座標・閾値（1920x1080基準）

### 変換式（提案）
定数:
```
xVP = 957, yVP = -649
K   = 2.79e-4     ( = cos(pitch)/f )
```
> **【第2回で更新】** この節は初回調査時の暫定値。**確定値は `xVP=960, yVP=−651, K=2.796e-4`**
> （F5・F6 で7動画・3解像度・10コート実測）。実装は下の「推奨アルゴリズム」節の定数を使うこと。
> 式の形はこのままで正しい。

フレーム毎パラメータ: `c0, c1, Xc`（c1 = K/Yc なので実質 Yc, Zc, Xc の3つ）

画面 (x,y) → コート (X,Z)（単位 m、原点=ネット中央、X=右方向、Z=奥方向）:
```
u  = y - yVP           // = y + 649
Z  = (1/u - c0) / c1
Yc = K / c1            // カメラ高さ(m)
X  = Xc + (x - xVP) * Yc / u
```
コート (X,Z) → 画面:
```
u = 1 / (c0 + c1*Z)
y = u + yVP
x = xVP + (X - Xc) * u / Yc
```

### 実測パラメータ例
| フレーム | c0 | c1 | Yc(m) | Xc(m) |
|---|---|---|---|---|
| t≈126.7s | 9.413e-4 | 3.043e-5 | 9.16 | -0.257 |
| t≈129.0s | 9.153e-4 | 2.442e-5 | 11.45 | -1.413 |

`Yc * c1 = 2.787e-4 / 2.796e-4` → 一定（Kの根拠）。

### 実測ライン位置（参考・A_t30 = 2026-08-20 10-44-35.mp4 t=30s）
- ファーベースライン y=187.5（x=566〜1505 に伸びる。相手キャラでx=920〜963が欠ける）
- ファーサービスライン y=312.5
- ネット上端テープ y=400(端)〜412.5(中央・たるむ) ※接地ラインではないので校正に使わない
- ニアサービスライン y≈820
- ニアベースライン 画面外（y>1080）
- y=190 での縦線: 左ダブルス 570.5 / 左シングルス 687.5 / 右シングルス 1384.5 / 右ダブルス 1501.5

### コート寸法（標準テニスコート・mでモデル化）
- ダブルス幅 10.97m（X = ±5.485）
- シングルス幅 8.23m（X = ±4.115）
- サービスライン Z = ±6.40
- ベースライン Z = ±11.885

実測でこの寸法が正しいことを確認した（F6）。Mario Tennis のコートは**実物と同じ比率**。
`(1/u@ファーBL − 1/u@ファーSL) / (1/u@ファーSL − 1/u@ニアSL)` の実測 = 0.4298、
規定寸法からの理論値 5.485/12.80 = 0.4285。誤差 0.3%。

### F6. 定数 K = 2.80e-4 は全コート・全解像度で共通（±0.5%）

  `Yc_report = ΔX / Δs`
- 経路B（奥行き）: 横ライン2本の `1/u` の差と、両者の実寸 Z 差から
  `c1 = Δ(1/u) / ΔZ`
- K = Yc_report × c1

| `11-33-43` @200 | 芝 | FHD | 16.08 | 1.728e-5 | **2.779e-4** |

   ダブルス（`00-39-45`）でも同じ値。**ダブルスも同一カメラモデル**。

**同時に得られた重要な事実**: `Yc_report` は 8.32〜16.08 m と**2倍近く動いている**。

### F7. カメラの内部パラメータが確定した

`xVP = 960`, `yVP = −651`, `K = cosθ/f = 2.796e-4` の3つから、θ（俯角）と f（焦点距離）が解ける:

```
f·tanθ = 540 − yVP = 1191
cosθ/f  = 2.796e-4
⟹ sinθ = 1191 × 2.796e-4 = 0.3330  →  θ = 19.45°（俯角）
⟹ f = cosθ / 2.796e-4 = 3372 px（1920x1080 換算）
⟹ 水平画角 2·atan(960/3372) = 32.1° / 垂直画角 18.2°
```

さらに `01-57-16` @500 の「ネット上端テープ」が見かけ Z=+2.84m に写ることから
カメラの Z 位置 Zc ≒ −30.9 m が逆算でき、
`Yc_true / tanθ = 10.87/0.352 = 30.9 m` と一致した。
→ **カメラの光軸はネット中央をぴったり向いている**。ドリーはこの光軸方向（斜め下向き）に沿った前後移動。

**yVP 誤差の感度**（`11-33-43` @200、Z既知の横ライン3本で c1 を2通りに計算した食い違い）:
| 仮定した yVP | c1 の2通りの食い違い |
|---|---|
| −637 | 0.7% |
| −649 | 0.3% |
| −661 | 0.07% |
→ **yVP を ±12px 間違えても Z 推定への影響は 1% 未満**。定数運用で問題ない。

## 推奨アルゴリズム

### 定数（全コート・全解像度・シングルス/ダブルス共通。1920x1080 換算）

```js
const XVP = 960.0;      // = W/2。ヨー0の帰結。厳密。
const YVP = -651.0;     // ±12 の誤差は Z 推定に 1% 未満しか効かない
const K   = 2.796e-4;   // = cosθ/f。実測レンジ 2.779〜2.807e-4
// 参考: θ=19.45°(俯角), f=3372px, HFOV 32.1°
// コート実寸（m。原点=ネット中央、X=画面右、Z=画面奥）
const X_DBL = 5.485, X_SGL = 4.115, Z_SVC = 6.40, Z_BASE = 11.885;
```

### フレーム毎パラメータは 3つだけ: `c0, c1, Xc`

```
u  = y - YVP                    // = y + 651
1/u = c0 + c1 * Z               // 奥行き（F4 で線形性を実測確認）
s  = (x - XVP) / u              // 横方向。1本の縦ラインで一定（F3・F5）
s  = (X - Xc) / Yc,  Yc = K / c1
```

画面→コート:
```
Z = (1/(y - YVP) - c0) / c1
X = Xc + (x - XVP) * (K / c1) / (y - YVP)
```
コート→画面:
```
u = 1 / (c0 + c1 * Z)
y = u + YVP
x = XVP + (X - Xc) * u * c1 / K
```

**必要な観測は「Z既知の横ライン2本」＋「X既知の縦ライン1本」の計3本だけ。**
- 横ライン2本 → `c0, c1`（2元1次）
- 縦ライン1本 → `s` を測って `Xc = X_known - s * K / c1`

### Step 1. 白線マスク（全コート共通・player-position F7 に F13 の下限を足したもの）

処理は **960x540 に縮小**して行う（720p 素材でも 1440p 素材でも同じ土俵に載る）。

```js
// フレーム自身のコート面輝度中央値
CL = median{ L(x,y) | y ∈ [0.35H, 0.92H], x ∈ [0.15W, 0.85W] }   // 3px 間引きで十分
isLine(x,y) = L > Math.max(CL * 1.06, 170) && (max(R,G,B) - min(R,G,B)) < 46
```
- **下限 170 は必須**（F13）。無いと石畳コートで目地が全部ラインになる。
  入れても他の9コートに影響は無いことを実測確認済み（F14）。
- 実測 CL（960x540）: 芝 150 / 砂 152 / クレイ赤 119 / 起伏芝 150 / 石畳 109 / 夜森 124 /
  青ハード 95 / ウッド 78 / 船・木甲板 77
- 全9コートでラインの L ピークは 185〜238、コート面の中央値は最大 158（court-robustness F5）。
  170 はその間に余裕を持って入る。

### Step 2. 横ライン検出（Hough を使わない・行プロファイル方式）★

素の Hough が金網・UI帯・ネットテープを上位に拾う問題（player-position F7b）は、
**「横ラインは画面水平（ロール0が実測確定）」という強い事前情報**を使えば Hough 自体が不要になる。

```
1. 行ごとに isLine 画素を数える → prof[y]
   ・除外: y_FHD < 130（上部バナー帯）
   ・除外: y_FHD > 860 かつ (x_FHD < 250 または x_FHD > 1670)（左右下のスコアUI）
2. prof[y] の極大（prof[y] >= prof[y±1] かつ > prof[y±2]）で
   prof[y] > 260（FHD換算px）のものをピークとする
3. 10px 以内のピークは最大値で1本にマージ
```
実測でこの手順は、芝/砂/クレイ赤/青ハード/船甲板/起伏芝すべてで
ベースライン・サービスラインを **n=600〜1400** の強いピークとして出した（雑ピークは n≈300〜500）。

**ピークの同定（どれがどのラインか）— 総当たり方式にすること ★**

**「最も上のピーク＝ファーベースライン」と決め打ちしてはいけない**（F14 実測）。
`23-19-09` @300 では最上位ピーク y=132 が正解だったが、票がいちばん多かったのは
y=256 のファーサービスラインのほうだった。背景の構造物が最上位に来る場合もある。

```
1. 上位N本（N=6〜8）のピークから2本を選ぶ組み合わせを列挙する
2. 各組に (Z=+11.885, Z=+6.40) / (+11.885, −6.40) / (+6.40, −6.40) …を割り当てて c0,c1 を求める
3. c1 ∈ [1.5e-5, 4.0e-5] に入らない組は棄却
4. 残りの全ピークを見かけ Z に変換し、
   +11.885 / +6.40 / 0 / −6.40 / −11.885 に ±0.5m で当たる本数を数える
   見かけ Z が +2.5〜+3.6 のピークは**ネットテープ**（F8）。当たり扱いにはするが Z 校正には使わない
5. 当たり本数が最大の組を採用。同点なら残差最小
6. 確定した3本以上で最小二乗して c0,c1 を再フィット
```
実測（F14）: 石畳・夜の森・起伏芝・クレイ赤の4ケースすべてで、この手順で
ファーBL / ファーSL / ネットテープ / ニアSL（夜の森ではニアBLも）が正しく同定できた。

**線が2本しか取れないフレーム**でも c0,c1 は解ける。1本以下なら Step 5 の引き継ぎへ。

**同定の交差検証**: Step 3 の s 投票から独立に `Yc = ΔX/Δs` が出る。
`K/c1` と一致しなければ（実測では 0.5〜0.7% で一致した）横ラインの同定を間違えている。
**この2経路チェックは実装必須**。ほぼ全ての同定ミスがここで捕まる。

### Step 3. 縦ライン検出 = s の1次元投票（★プロトタイプ実装で9コート検証済み・F11）

**消失点が (960, −651) に固定という事実を使えば、縦ラインは 1パラメータ（s）だけの探索になる。**
Hough の2次元投票（rho,theta）が **1次元投票（s）**に落ちる。
金網・パラソル・観客席・森の落ち葉はどれも消失点を通らないので、票が1つの bin に積み上がらず**自動的に落ちる**。

**そのまま実装できる擬似コード**（実測でこの通り動いた）:
```js
const SMIN = -1.2, SMAX = 1.2, DS = 0.002;        // 1200 bin
const vote = new Float64Array((SMAX - SMIN) / DS);
for (let y = y0; y <= y1; y++) {                  // y0..y1 は FHD で 300..1050 が既定
  // 横ラインが乗っている行は s 方向に票を撒き散らすので丸ごと飛ばす
  if (rowLineCount(y) > 900) continue;            // FHD換算px
  const u = y - YVP;
  for (let x = 0; x < W; x++) {
    if (y > 860 && (x < 250 || x > 1670)) continue;   // 左右下のスコアUI
    if (!isLine(x, y)) continue;
    const b = ((x - XVP) / u - SMIN) / DS | 0;
    if (b >= 0 && b < vote.length) vote[b] += 1;      // 重みは FHD 換算 px
  }
}
// ±2bin 平滑 → 半径5bin の非極大抑制 → 票 120 以上をピーク採用
// ピーク位置は前後±4bin の重心でサブbin精度に上げる
```

**ピークの同定（1 : 3 : 3 : 1 パターン）**
コートの5本の縦ラインの X は −5.485 / −4.115 / 0 / +4.115 / +5.485。
隣接間隔は 1.370 : 4.115 : 4.115 : 1.370 = **1 : 3 : 3 : 1**。
実測 9コートすべてでこの比が **1 : 2.92〜3.01 : 1.00±0.03** で出た（F11 の表）。
```
1. ピークを s の昇順に並べる
2. 隣接ギャップを最小ギャップで割った比を作る
3. 1.370m を単位にすると、取りうるギャップは 1 / 3 / 4 / 6 / 7 / 8 のいずれか（重複なし）
   → 3本や4本しか取れなくても、ギャップ比だけで各ラインの X が一意に決まる
4. Yc_report = ΔX / Δs（複数の組で求めて中央値）
   Xc = X_known − s · Yc_report
```
**Step 2 が先に済んでいれば `Yc = K/c1` が既知**なので、期待される Δs
（アレー = 1.370/Yc、シングルス半幅 = 4.115/Yc）を直接照合できる。
この場合は**縦ライン1本でも Xc が解ける**（そのラインの X が同定できればよい）。

**実測ピーク（`23-37-24` @300s）**: −0.4378 / −0.3199 / +0.0280 / +0.3761 / +0.4941
→ ギャップ 0.1179 / 0.3479 / 0.3481 / 0.1180 = 1 : 2.95 : 2.95 : 1.00

### Step 4. ロバスト化（実測に基づく具体策）

- **走査行の刻み**: 横ラインの行プロファイルは全行（960x540 なら 540行）でよい。
  s 投票は全画素走査でも 960x540 = 518k、Node で 1フレーム数ms。60fps に十分間に合う。
- **プレイヤー・エフェクトによる分断**: 横ライン検出は行カウント、縦ラインは投票なので
  キャラで数十px欠けても順位は変わらない。**RANSAC より投票方式のほうがこの用途では堅い**（実測）。
- **横ライン行を投票から除く**のは必須。除かないとベースライン1本が s 全域に票をばら撒く。
  実装は上の `rowLineCount(y) > 900`（FHD換算px）で足りた。
- **夜の森コート**（`11-02-43`）: 背景の落ち葉で isLine 該当率が 26.6% になるが、
  **s 投票なら 5本すべて正しく取れた**（F11）。追跡／Hough 方式は 0本だった。
  **この1点だけでも投票方式を選ぶ理由になる。**
- **石畳コート**: 目地が白線と同条件になる（player-position F7）。目地は**格子状で消失点を通らない**ので
  s 投票では分散して落ちるはず（`01-57-16` の石畳区間では未検証 → 未確認）。
- **エフェクト・フラッシュ**: F12 の通り isLine 該当率 > 15% は要注意。ただし**即棄却にはしない**
  （夜の森が 26.6% で正常なため）。**ピーク比 1:3:3:1 が成立するか**を採否の基準にする。

### Step 5. 線が足りないフレームの補間・引き継ぎ

パラメータ (c0, c1, Xc) は**時間的に非常に滑らかに動く**（court-robustness F4 実測: 0.2秒で 3px 以下）。

```
優先度:
 A. 横2本＋縦1本 → 完全解。そのまま採用
 B. 横2本のみ    → c0,c1 は解ける。Xc は前フレームから引き継ぐ（横方向のドリーは
                    1秒で 30px≒0.3m 程度なので 0.2秒なら誤差 0.06m）
 C. 横1本＋縦1本 → c1 を前フレームから引き継ぎ、c0 を横ライン1本で更新、Xc を縦ラインで更新
 D. 何も取れない → 直前の有効フレームの値を保持。**0.25秒（15フレーム）を超えたら無効**にして
                    そのラリー区間を解析対象外にする
```
- 状態は `(c0, c1, Xc)` の3次元。**等速度モデルのカルマン/α-βフィルタ**を掛けると
  1フレームだけのミス検出が吸収できる。プロセスノイズは実測値から
  `c1: ±3e-7/frame`, `Xc: ±0.01m/frame` 程度。
- **前後両方向から補間できる**（オフライン解析なので未来のフレームが使える）。
  D の欠測区間は前後の有効フレームで線形補間するのが最も精度が高い。

### Step 6. 「今が標準のラリー視点か」の高速判定（前段ゲート）

サーブ画・Change Court 演出・得点演出（金メダル）・フィーバーカットイン・リプレイ・
Winner画面・マッチング画面を弾く。**判定Aだけで実質足りる**（実測で全ケース分離できた）。

```
判定A（本命）— 横ライン2本の整合性
  1. 行プロファイルのピークのうち最も上の強いものを Z=+11.885 と仮置き
  2. 次の強いピークを Z=+6.40 と仮置きして c1 を計算
  3. c1 ∈ [1.5e-5, 4.0e-5] に入るか（実測レンジ 1.73e-5〜3.37e-5 の外側に少し余裕を持たせた）
  4. 残りのピークを見かけ Z に直したとき、+6.40 / 0 / −6.40 / −11.885 / ネットテープ(+2.5〜+3.6)
     のいずれかに ±0.5m で当たるものが1本以上ある
  → 全部通れば標準ラリー視点

判定B（補助・より安く弾きたいとき）
  ・s 投票のピーク比が 1 : 3 : 3 : 1（許容 ±8%）になる（F11 実測: 全9コートで成立）
  ・得点ピップのカプセルが左右とも見えている（court-robustness F6: 全コート不透明・座標固定）
    x 20..220 / 1700..1900, y 986..1037 に黒枠+白リングがある
  ・isLine 該当率（F12）: 3.9〜11.2% が正常。> 15% なら判定B を必ず併用する
```

**サーブ画を弾く最も安い判定（F10 由来・強く推奨）**
```
横ラインの「傾き」を1本測る:
  同じ横ラインの y を x=400 と x=1500（FHD）で読み、差 |Δy| > 25px ならサーブ画
実測: ラリー画 Δy = 0（3コートで厳密に 0）/ サーブ画 Δy = ±63〜64px
```
2列の走査だけで済み、誤判定の余地がほぼ無い。

**弾くべきものの実測特徴**

| シーン | 実測特徴 | 弾き方 |
|---|---|---|
| サーブ画（`10-44-35` @300, `22-18-37` @175） | 横ラインが ±3.3° 傾く。空が上部を占める | 上の傾き判定 |
| Change Court（`22-18-37` t≈139〜145） | 地面すれすれの別カメラ＋白文字。約6秒 | 判定A が通らない |
| 得点演出（`22-02-04` @400, `23-59-59` @300） | 金メダルが全画面。isLine 17.4〜17.7% | 判定A＋isLine率 |
| ゲーム間バナー（`22-18-37` @173） | 斜め俯瞰＋名前バナー。isLine 5.4% だが横ラインが取れない | 判定A |
| フィーバーカットイン／マッチング（`01-08-30` @300） | コートが写らない。isLine 2.6% | 判定A |

実測: `01-08-30` @300s（マッチング画面）を無理に縦ライン検出にかけると
「x が y に依存しない完全な直線 2本（b=0.0000）」が出た。
**b が厳密に 0 の縦線＝UI の枠線**なので、`|b| < 0.02` は必ず捨てる
（s 投票方式では u で割るため、UI 枠線は s が y ごとに変わって票が分散し、自然に落ちる）。

### Step 7. コートチェンジの検出（背景依存の処理をしている場合のみ必要）

F9 の通り Change Court でカメラ・プレイヤーの上下関係は変わらないが、**背景は左右入れ替わる**。
背景の時間中央値・影の方向・場外構造物マスクを使っている処理は、
**Change Court のたびにリセットする**こと。

検出は「約6秒間、判定A が連続して落ちる区間」で足りる（`22-18-37` t≈139〜145 で実測）。
得点ピップは Change Court 中も表示され続けるので、
「ピップは見えるが判定A が落ちる区間が 3〜8秒続いた」＝ Change Court、と切り分けられる。

### 参考: 精度の目安（実測から）

- 5本の縦ラインが取れるフレームでは、独立3制約が **0.5% 以内で一致**（F6）。
  コート幅 10.97m に対して 0.5% = **±5cm**。
- 砂コートで、s 投票から出した Yc=10.05 と横ライン＋K から出した Yc=10.04 が **0.1% で一致**（F11）。
- 横方向の分解能: s の刻み 0.002 × Yc(8〜16m) = **1.6〜3.2 cm/bin**。実装上はサブbin重心を取るのでさらに細かい。
- 奥行きの分解能: `|dZ/dy| = 1/(c1·u²)`。c1=2.4e-5 のとき
  ネット付近（u=1500）で **1.9 cm/px**、ファーベースライン付近（u=850）で **5.8 cm/px**。
- **奥ほど誤差が大きい**のは原理的。ファーベースライン際のイン/アウト判定には ±10cm を見込むこと。
- 全体としては、**ラリー分析で使う 1.5m 程度のゾーン分解能なら余裕で足りる**。

## 落とし穴

1. **ネットのテープを水平基準に使わない**。中央がたるんで最大12px下がる（A_t30: 端400 / 中央412.5）。
   接地ラインではないので Z 換算もできない。ただし**見かけ Z=+2.5〜+3.6 に出る**ので**同定して捨てる**のは容易（F8）。
2. キャラクター・エフェクト・スコアUIがラインを分断する。
   → 行カウント／1次元投票にすれば自動的に吸収される。区間分割を明示的に扱う必要はない。
3. ニアベースラインは画面外に出るフレームが多い（A_t30 は y>1080）。9コート中5つで画面外/HUD裏。
   常に見える保証があるのは**ファーベースラインとニアサービスライン**。
4. **消失点の x は 957 ではなく 960（画面中央）**。前回レポートの 957 は1動画からの推定値。7動画平均 959.4（F5）。
5. **横ラインの投票除外を忘れると s 投票が壊れる**。ベースライン1本で s 全域に票が撒かれる。
6. **`|b| < 0.02` の「縦線」は UI 枠線**。s 投票なら自動で落ちるが、直線フィット方式では必ず除外すること。
7. **サーブ画は横ラインが ±3.3° 傾く別カメラ**（F10）。標準モデルを当てると数メートル単位で狂う。
   2列だけ走査する傾き判定（Δy > 25px）で確実に弾ける。
8. **isLine 該当率が高い＝ダメ、ではない**。夜の森は 26.6% でも s 投票なら正解する（F11/F12）。
   得点演出（17.4〜17.7%）と区別するには**ピーク比 1:3:3:1** を見る。
9. **Change Court で背景が左右入れ替わる**（F9）。ホモグラフィには影響しないが、
   背景中央値・影方向・場外マスクを持っている処理は作り直しが要る。
10. **`Yc_report` は真のカメラ高さではない**。`Yc_report = Yc_true / cosθ`（θ=19.45° なので 7% 大きい）。
    実寸として扱いたいときは `Yc_true = Yc_report × 0.943`。座標変換の式にはそのまま `Yc_report` を使うのが正しい。
11. **`K = cosθ/f` であって `cos²θ/f` ではない**（`Yc_report` の定義とセットで意味が決まる）。
    式を触るときは `Yc_report = K/c1` と `X = Xc + (x−960)·Yc_report/u` を必ずセットで扱うこと。

  平面近似は成り立っている様子だが、**ボールのバウンド位置など高さが効く量では起伏が誤差になる**可能性。
  丘の高低差そのものは測っていない。
- **ダブルスは `00-39-45` の1本しか確認していない**。カメラモデルは同一だったが、
  4人が同時に写ってラインを隠すぶん検出率が落ちるかは未測定。
- **リプレイ／スロー演出中のカメラ**。標準ラリーと同じモデルかは未確認（判定Aで弾く前提にしてある）。

  ラリー画自体は標準モデルで解けたが、発動前後の連続性は追っていない。

**サーブ画（別モデル）**

- **サーブ動作中（トス〜インパクト）にカメラがどう動くか**。1秒で 8px の緩いドリーは確認したが、
  打った瞬間にラリー画へどう遷移するかは未追跡。

**運用面**
- **フレーム間ジッタの実測**。パラメータの時間的滑らかさは court-robustness F4 の並進量からの推定で、
  `(c0,c1,Xc)` を連続フレームで実際に解いて分散を測ってはいない。
  **Step 5 のフィルタ定数（c1: ±3e-7/frame, Xc: ±0.01m/frame）は推定値**。実装時に測り直すこと。
